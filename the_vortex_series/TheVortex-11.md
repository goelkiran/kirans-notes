# Reimagining the software development lifecycle — from scratch, not from memory

*Kiran's Notes — The Vortex, Article 11 of 12*

---

The software development lifecycle we use today was not designed.

It was accumulated.

Layer by layer, over decades, as responses to failure. Waterfall. Agile. DevOps. Continuous delivery. Each one solving a problem the previous one exposed.

Each one calibrated to human teams, human speed, and human limitations.

What we have never done is start from first principles and ask:

If we were designing this today — with the participants we now have — what would it look like?

---

## What the current SDLC is optimised for

Look closely at a modern SDLC — sprint planning, standups, code review, QA cycles, release approvals.

Almost every one exists to compensate for a human failure mode.

Humans lose alignment → standups.

Humans make mistakes → code review.

Humans miss edge cases → QA.

Humans struggle with long feedback loops → sprints.

These are not arbitrary rituals. They are precise responses to observed patterns of failure.

The question now is not whether they were right.

It is whether they are still calibrated to the system we have.

---

## What does not change

Some things do not move.

The need for human-defined intent remains.

Someone still needs to understand the problem deeply enough to specify what should be built — and to evaluate whether the system solves the real problem, not just the stated one.

The need for accountability remains.

Someone must be able to explain and stand behind what the system does.

The need for adversarial evaluation remains — and intensifies.

As we saw earlier in the testing discussion, when coder and tester share assumptions, testing becomes confirmation.

That distance must now be designed deliberately.

---

## What might change

Some things are worth questioning.

The two-week sprint was a human constraint — not a technical one. When iteration cycles compress from weeks to hours, cadence needs to be reconsidered.

Code review shifts meaning. It becomes less about syntax and more about intent.

Testing pipelines evolve. Some stages become more important. Others become automated. The structure itself needs rethinking.

These are not small adjustments.

They are shifts in what the system is optimised for.

---

## The shape of a different SDLC

I do not have a finished methodology.

What I have is a direction.

Design around accountability, not just delivery.

Separate intent from execution — make the human contribution explicit.

Maintain adversarial distance — between generation and validation.

Build provenance into the system from the start.

Review for meaning, not for form.

None of these are new ideas.

But in the current system, they are often implicit.

In the system we are moving toward, they need to be explicit.

---

## One final observation

Every version of the SDLC we have built so far has been a response.

A response to failure.

This is the first time we have the chance to design proactively.

Not from memory.

From first principles.
